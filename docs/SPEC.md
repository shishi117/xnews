# Xニュース収集ツール 仕様書

最終更新時点の実装内容をまとめたもの。設定値を変えた場合はこの文書ではなく
`src/x_collector.py` の該当行が正。迷ったらコードを見る。

---

## 1. 目的

X（Twitter）の英語ニュース速報アカウント2件から、当人のオリジナル投稿の未取得分を
定期的に集め、ローカルLLMで日本語訳＋任意の軸でラベリングしたうえで、HTMLメールで
配信する。あわせて溜まったデータをブラウザで一覧・絞り込みできるビューアを添える。

## 2. アーキテクチャ（構成b: 全ローカル1本）

- 収集・保存・翻訳・配信のすべてを **1本の Python スクリプト（`x_collector.py`）** で完結させる。
  GAS/Google Sheets は使わない（要件定義の構成a/b比較で b を採用）。
- **翻訳・ラベリングだけ Groq**（クラウド推論・無料枠・OpenAI互換）を呼ぶ。収集・保存・
  メール送信はLLMが無くても動く（`--collect-only` 参照）。
  - ★以前はDocker上のOllama（ローカルLLM）だったが、**PC負荷が高すぎたため廃止**した。
    Docker/GPUは不要になった。
  - **引き換えに、投稿の原文がGroqへ送信される**（収集対象は公開投稿だが、
    「全ローカル」ではなくなった点は認識しておくこと）。
- 秘密情報（メールのアプリパスワード・Xの捨て垢セッション）は **`config/config.ini` に集約**。
  ローカル運用ではこれで完結する。
  - **クラウド運用（GitHub Actions）の場合は例外的に環境変数を使う**（`secret()`関数、§10）。
    config.iniをリポジトリに置けないため、config.iniの値が無いときだけ同名の環境変数
    （GitHub Secretsから渡される）にフォールバックする。ローカル運用には影響しない。
    手順は `docs/CLOUD_SETUP.md`。

```
python src/x_collector.py
            ├ ① 収集（curl_cffi + 捨て垢セッション or ゲスト）
            ├ ② SQLiteへ冪等保存（news_log / news_labels）
            ├ ③ 翻訳＋ラベリング（Groq）
            ├ ④ 保持期間(7日)超過の削除
            ├ ⑤ ラベルの表記ゆれ統一（Groq・DB全体が対象）
            ├ ⑥ HTMLメール送信（Gmail SMTP）
            └ ⑦ DBをJSON化してdata/news_data.jsへ書き出し、db_viewer.htmlをfile://で自動オープン
                （サーバは使わない。§8・§9）
```

一連の流れは `run.bat` が①〜⑦をまとめて実行する。

| `financialjuice` | 捨て垢セッション必須 | ゲストAPIだと古いキャッシュしか返らない実測あり |
| `DeItaone` | 捨て垢セッション必須 | 同上 |

## 4. 収集仕様

### 4.1 認証
- **ゲスト**：`curl_cffi` でXの内部GraphQL（`UserTweets`/`UserByScreenName`）を直叩き。
- **捨て垢セッション**：`config.ini` の `auth_token`/`ct0`（ブラウザのCookie）を使い、
  ログイン済みとして同じGraphQLを叩く。取得手順は `auth-session-setup.md`。
- Bearerトークン・`queryId`・`features` は `x_collector.py` 冒頭に定数として埋め込み。
  **これらはXが2〜4週ごとに変更することがある**。404/400が出たら実機DevToolsで
  現行値を採り直して差し替える（手順はコード内コメント参照）。

### 4.2 ページネーション
- `COUNT=40` を要求するが、Xは厳密に守らない。**実測では1ページ約20件**だった。
- 1ページで指定範囲に届かないアカウント向けに、カーソルで追加ページを
  取得する（`paginate_tweets`）。`MAX_PAGES=10` で必ず打ち切る。
- **打ち切り条件は「そのページに窓内の投稿が1件も無い」＝窓を追い越した時点**。
  - ★以前は「ページ内の最古が窓より古ければ終了」としていた。**ピン留めツイートは
    何年も前の日付でページ先頭に混ざる**ため、これだと1ページ目で必ず打ち切られる。
    実機で `raw 21 / pages 1`、8時間の窓のうち直近3時間ぶん（20件）しか取れず、
    **4.75時間ぶんを取りこぼしていた**。selftest (f) が再発防止の回帰テスト。
  - `cursorが無い` / `cursorが進まない` / `MAX_PAGES到達` でも止まるが、これらは
    **窓を覆う前の打ち切り＝取りこぼしの可能性**があるため `[ALERT]` を表示する。
- 実行ログに1ページごとの `件数 / 窓内 / 時間幅 / cursorの有無` を出す。
  ページが増えない場合はここで `cursor=無` かどうかを確認する
  （`cursor=無` が続くなら、DevToolsで `UserTweets` の cursor-bottom の実際の
  キー名を確認し `extract_cursor` を調整する。キー名 `cursorType`/`value` は未検証）。

### 4.3 本人オリジナル判定
以下を満たすツイートだけを対象にする（`filter_originals`）：
- 著者(screen_name)が対象handleと一致（大小無視）
- RT でない（`retweeted_status_result` を持たない／本文が `RT @` で始まらない）
- 引用でない（`is_quote_status` が真でない／`quoted_status_result` を持たない）

### 4.4 収集する時間帯・差分

**既定は時間範囲モード**（日本時間で「当日の何時から何時まで」を指定する）。

| 指定 | 意味 |
|---|---|
| （引数なし） | 当日 `DEFAULT_RANGE_FROM`〜`DEFAULT_RANGE_TO`（既定 **0:00〜8:00 JST**） |
| `--from 8:00 --to 18:00` | 当日の8〜18時（JST） |
| `--from "2026/09/23 22:00" --to "09/24 02:00"` | 日付をまたぐ指定 |
| `--from 22:00 --to 2:00` | `to <= from` は翌日扱い（＝4時間） |
| `--window 8` | 旧方式（実行時刻から遡って8時間） |

- 時刻の書式は `8:00` / `08:00` / `09/24 8:00` / `2026/09/24 8:00`。不正な書式は
  トレースバックではなく `[FAIL] 時刻の書式が不正です` で終了する（終了コード2）。
- **両端とも含む**（`start <= 投稿日時 <= end`）。`0:00〜8:00` と `8:00〜12:00` を
  続けて実行すると 8:00 ちょうどの投稿は両方に該当するが、`state.json` の差分除外で
  2回目は送られない。
- Xの内部APIに時間範囲の指定は無い。**新しい順にページを辿り、範囲の下端を
  下回るまで遡る**（§4.2）。範囲を長く取るほどページ数が要る。
- **`state.json`**：アカウントごとに `last_seen_id`（送信済みの最大ツイートID）を保持し、
  `id > last_seen_id` で重複を除外する（同じ実行内の重複はDB側の主キーでも防止）。
  - ★高水位は**範囲内の最大ID**。ページ送りの都合で raw には範囲より新しい投稿も
    入るが、それらは「送信済み」にしない（まだ配信していないものを取りこぼさないため）。
  - **過去の時間帯を指定し直しても、送信済みIDより小さいものは配信されない**
    （仕様。取り直したい場合は `state.json` の該当handleの行を消す）。
- 窓を覆えたかどうかは**毎回ログで確認できる**（`打ち切り=窓を覆った` なら取りこぼし無し）。

## 5. データベーススキーマ（`news_log.db` / SQLite）

### `news_log`（1行＝1ツイート）
| 列 | 内容 |
|---|---|
| `tweet_id` (PK) | 重複排除キー |
| `created_at` | 投稿日時（JST, `yyyy/MM/dd HH:mm`） |
| `keyword` / `level` / `rank` | 旧GAS互換の空列（v0では未使用） |
| `title` | 原文冒頭60字 |
| `summary` | 原文全文 |
| `url` | permalink |
| `source` | `X @handle` |
| `translation` | 日本語訳（`enrich()`が後から埋める。NULLは未処理の印） |

### `news_labels`（縦持ち・1行＝1ツイート×1軸）
| 列 | 内容 |
|---|---|
| `tweet_id` | news_log.tweet_id |
| `axis` | 軸名（`LABEL_AXES` の要素。自由に増減可） |
| `value` | その軸でのLLM判定値 |
| PK | `(tweet_id, axis, value)` |

★主キーに `value` を含めるため、**1つの軸に複数の値を持てる**（例: 国・地域が
「イラン」と「米国」の2行）。旧スキーマ（主キー `(tweet_id, axis)`）のDBは
起動時に `migrate_labels_pk` が自動で作り替える（冪等）。

軸の個数・名称を変えても **スキーマ変更は不要**（`LABEL_AXES` を編集するだけ）。
旧バージョン（固定 `genre`/`country` 列）のデータは起動時に自動で `news_labels` へ
一度だけ移行される（`init_db`。冪等・何度起動しても安全）。

## 6. ラベリング仕様（ローカルLLM）

- 接続先：`LLM_BASE = https://api.groq.com/openai/v1`（OpenAI互換）。APIキーは
  `config.ini` の `[llm] api_key`（console.groq.com/keys で発行。クレジットカード不要）。
- モデル：`LLM_MODEL = openai/gpt-oss-120b`（`config.ini` の `[llm] model` でも上書き可）。
  - ★2026/06/17に `llama-3.3-70b-versatile` / `llama-3.1-8b-instant` の
    無料・開発者ティアでの非推奨がアナウンスされ、後継として `openai/gpt-oss-120b` /
    `openai/gpt-oss-20b` / `qwen/qwen3.8-27b` が案内されている。
  - `llama-3.3-70b-versatile` / `llama-3.1-8b-instant` は **2026/08/16に無料・開発者
    ティアで停止**（Llama系はEnterpriseティアへ移行）。設定に残っていると
    `HTTP 404 ... does not exist or you do not have access to it` になる。
  - **`python src\x_collector.py --list-models`** で、そのAPIキーで実際に使える
    モデルIDを一覧できる（GET /models）。ドキュメントを読むより確実。
- **レート制限（無料枠）**：目安は30リクエスト/分・6,000トークン/分（組織単位・モデル単位）。
  既定は内側に取って `LLM_RPM=25` / `LLM_TPM=5000`（`config.ini` で変更可）。
  - `RateLimiter` が直近60秒のリクエスト数とトークン数を見て、超えそうなら送信前に待つ。
    先に当たるのは**トークン**の方（1件あたり600トークン前後なら毎分8件程度が上限）。
  - 429が返ったら `retry-after` ヘッダ（無ければ本文の `try again in 6m 11.52s`）に
    従って待ち、最大 `LLM_MAX_RETRY=6` 回まで再試行する＝**待ってでも全件処理する**方針。
  - 400（モデル名ミス等）は待たずに即失敗させる。
- ★**User-Agent必須**。GroqのAPIはCloudflareの背後にあり、Pythonの既定UA
  （`Python-urllib/3.x`）は**APIキーが検証される前に**エッジで弾かれ、
  `HTTP 403: error code: 1010`（ブラウザ整合性チェック）になる。実機で発生した。
  `LLM_USER_AGENT` を必ず送る（値は何でもよい）。selftestに回帰テストあり。
- エラーは原因別のメッセージにする: 403(1010)=UA、401=APIキー、404=モデル名。
  いずれもリトライせず即失敗させる（待っても直らないため）。
- ★**推論モデル（gpt-oss / qwen3系）への対応**。これらは隠れた推論トークンが
  出力予算を共有するため、予算が小さいとJSONを書き始める前に打ち切られ、
  `HTTP 400 json_validate_failed`（`failed_generation` が空）になる。実機で発生した。
  対策は3段:
  1. `max_completion_tokens` に `LLM_REASONING_HEADROOM=1500` を上乗せする
     （`max_tokens` は非推奨なので現行名に変更済み）
  2. `reasoning_effort=low` を送る（翻訳・分類なので深い推論は不要）。
     受け付けないモデルなら、その項目を外して自動再試行する
  3. それでも `json_validate_failed` なら **JSONモード(`response_format`)を外して再試行**。
     `parse_enrich`/`parse_normalize` は元々ゆるくパースするので素のテキストでも通る
- レート制限の見積りは**出力トークンの実測平均**（EMA）を使う。予算満額で見積もると
  上限が過剰に効いて極端に遅くなるため。
  - 実測（モックで22件＋正規化4回を通した検証）では、**待ち合計180秒**で全件完了した。
- プロンプトで「該当なしは『なし』と書く（`-` `…` `—` `無` などの記号を使わない）」
  「値は日本語」「その軸に合わない語を入れない」を明示している。実機で `-` や `…` が
  乱立し、正規化側で吸収しきれなかったため（`経済政策: -→経済政策` のような誤統合も発生）。
- 対象軸：`LABEL_AXES = ["国・地域", "業界", "経済政策", "金融機関"]`
  （個数・内容とも自由。増減してもコード変更は軸リストの1行のみ）。
- **軸を減らしたとき**：DBに残る旧軸の行はメールにもメール用の集計にも出ない
  （`fetch_labels` が `LABEL_AXES` で絞る）。正規化の対象からも外れる。
  DBの行自体は保持期間(7日)で自然に消えるが、すぐ消したい場合は
  `python src\x_collector.py --prune-axes` を実行する。
  なお `db_viewer.html` はDBの中身をそのまま見せる設計なので、消すまでは旧軸も表示される。
- 1回のLLM呼び出しで「日本語訳」と「全軸ぶんの値」を同時にJSONで受け取る
  （`enrich_prompt`）。LLMが答えなかった軸は自動的に `"不明"` で埋める
  （`parse_enrich`。欠測にしない）。
- `translation` が空の行だけを対象に処理するため、**再実行しても既処理分は再送信されない**。

## 6.4 バッチ処理（複数件まとめてのAPI呼び出し）

★2026/09時点、`enrich()` は**1件ずつ**ではなく `ENRICH_BATCH_SIZE`（既定10件。
`config.ini` の `[llm] batch_size` で上書き可）ずつまとめて1回のAPI呼び出しで処理する。
無料枠は**RPM（リクエスト数/分）にも上限があり**、1件ずつ叩くとまずRPMに当たって
待ち時間が支配的になる（実測で104件が1件ずつだと大半が待ち時間）ため、呼び出し回数
そのものを減らす狙い。

- プロンプト（`enrich_batch_prompt`）はツイートIDをキーにしたJSONオブジェクトを渡し、
  「`{"items": {"<id>": {"translation":…, "labels":{…}}, …}}` の形式で、
  **全キーぶん必ず回答すること**」と明示して返させる（`ENRICH_BATCH_SYS`）。
- 出力予算はバッチ件数から見積もる（`min(4000, 220*件数+200)`）。固定値だと
  件数が多いとき途中でJSONが切れるため。
- レート制限の見積り（`RateLimiter`への事前申告）も `llm_chat(..., est_items=件数)` で
  件数ぶんスケールさせる。1件ぶんの実測平均（`_observed_output()`）のまま見積もると
  バッチ時に過小評価してTPM超過（429連発）を招くため。
- **失敗時の扱い（`normalize_labels`のチャンク半分割と同じ考え方）**:
  1. バッチのAPI呼び出し自体が例外（500・コンテキスト超過等）で失敗した場合、
     **バッチを半分に分割して再試行**する。1件になっても失敗する場合は
     `enrich_one()`（中国語再試行つきの従来の1件処理）にフォールバックする。
  2. バッチ呼び出しは成功したが、**一部の項目だけ回答漏れ・翻訳が空・中国語混入**
     だった場合は、その項目だけ `enrich_one()` で個別に立て直す
     （バッチ内の他の項目の成功を巻き込んで捨てない）。
- 進捗表示・DBへのコミットは**1件ごと**（バッチ内の一部だけ処理された場合でも、
  成功した項目から順にコミットする＝途中で中断しても既処理分は残る）。
- `--selftest` にバッチ成功時の回答漏れ/中国語混入フォールバック、バッチ失敗時の
  半分割→個別フォールバック、`est_items` がレート見積りに反映されることの
  回帰テストがある。

## 6.5 ラベルの表記ゆれ統一（`normalize_labels`）

1件ずつのラベリングでは「米国 / アメリカ」「なし / 無 / ×」のように表記が割れる。
そこで **メール送信の直前に、DB内の全ラベルをLLMに見せて代表表記へ寄せ直す**。

- 対象は新規ぶんだけでなく **DB全体**（既存の行も書き換わるので、過去分と表記が揃う）。
- 軸ごとに、現存する値の一覧をLLMへ渡して `{"mapping": {"元の値": ["代表表記", ...]}}`
  を受け取る。値が30個を超える軸は分割して問い合わせ、確定済みの代表表記を次の
  問い合わせに引き継ぐ（チャンクを跨いでも表記が割れないようにするため）。
- **1つの値に複数の対象が含まれる場合は分割**する（`"イラン, 米国"` → 2行）。
  分割はLLMに判断させるので、`"ゴールドマン・サックス"` のような固有名詞の「・」では
  割れない（ルールベースの区切り文字分割では誤爆するため、この方式にした）。
- 1回の問い合わせは `NORMALIZE_CHUNK = 15` 値まで。**サーバが500を返した場合は
  チャンクを半分に割って再試行**する（Ollama時代に、値30個の軸でコンテキスト超過により
  `HTTP Error 500` となりその軸だけ正規化されなかった実績がある。Groqは
  コンテキストが桁違いに大きいので発生しにくいが、安全側のまま残している）。
  出力上限は値の数から見積もる（固定2000をやめた）。
- 値が1種類しかない軸も対象にする（`"イラン, 米国"` がその軸で唯一の値だと分割されない、
  という穴があったため）。
- 書き換えは**軸ごとに独立**。LLMが壊れた応答を返した値は「元のまま」に倒し、
  例外が出た軸はロールバックして他の軸の結果は残す（ラベルを失わない）。
- **実測**（123件・2026/09/24時点）: 国・地域 33種類→16種類、金融機関 20→11、
  経済政策 23→20。`ゴールマン・サックス` と `ゴールマン Sachs` のような
  **誤記の統合はできるが、正しい表記に直るとは限らない**（モデル依存）。

## 6.6 保持期間（`purge_old`）

- `RETENTION_DAYS = 7`。`news_log.created_at`（JST・投稿日時）を基準に、
  それより古い行を `news_log` と `news_labels` の両方から削除する。毎回の実行で走る。
- `state.json` の `last_seen_id` は消さないため、**削除済みのツイートが再収集されることはない**。
- 本体の無い孤児ラベル行もここで掃除する。

## 7. メール仕様

- 送信：Gmail SMTP（587, STARTTLS）＋アプリパスワード。設定は `config.ini` の `[mail]`。
- 件名：`【Xニュース】yyyy/MM/dd`。
- **レイアウト**：`EMAIL_GROUP_BY`（現在 `"国・地域"`）の値ごとにセクション分けし、
  各セクション内は「左に縦線＋ドット、右にコンパクトカード」のタイムライン表示
  （時刻・取得元・訳文・他軸バッジ）。セクション自体も内容も時系列（新しい方が上）を維持。
  セクション見出しの色・バッジの色は文字列から決定的に算出（`axis_color`）するため、
  軸の値が増減してもハードコードのマップ不要。
- `<meta charset="UTF-8">` を明示（無いと一部の表示経路で日本語が文字化けする実害を確認済み）。
- 送信後（成功・失敗いずれでも）、db_viewer が自動的に開く（§9）。

## 8. db_viewer.html 仕様

- `news_log`/`news_labels` の中身をブラウザで一覧・検索・絞り込みできる単一HTMLファイル。
- ★2026/09時点、**ローカルサーバは廃止**した。`file://` で直接ダブルクリックして開く
  運用に一本化している（旧版は `http.server` を裏で起動していたが、`config/config.ini` を
  含むプロジェクトルート全体を全インターフェースへ配信してしまう問題があったため、
  「サーバを立てない」設計に変更した＝この問題自体が構造的に解消される）。
- **読み込み元はSQLiteではなくJSON**（`data/news_data.js`）に変更した。
  `x_collector.py` が `news_log`/`news_labels` を tweet_idごとに
  `{tweet_id, created_at, source, translation, summary, url, labels:{軸:[値,...]}}` へ組み立て、
  `window.__NEWS_ITEMS = [...]` という形で書き出す（`build_viewer_items`/`write_viewer_data`）。
  - `file://` はブラウザの `fetch` によるローカルファイル読み込みを禁止するが、
    `<script src="...">` の読み込みは禁止されない。この性質を使い、
    `news_data.js` を素の `.js` ファイルとして `<script>` タグで読み込む
    （以前はSQLite本体をbase64にして同じ手法で読んでいたが、ブラウザ側でSQLを実行する
    必要が無いのでJSONへ単純化し、あわせて `sql.js`（SQLiteのWASM実装）の埋め込みも
    丸ごと削除した＝db_viewer.html自体が約945KB→約18KBまで小さくなった）。
  - 読み込み経路は**この1本のみ**（`file://` 直開き固定・ファイル選択ボタンは無い）。常に
    「最後に `x_collector.py` を実行した時点」のデータになる（サーバが無いので
    ブラウザを開いたまま自動更新はされない。最新を見るには再実行してから開き直す）。
- 1軸に複数値がある場合、バッジは値ごとに1つ表示し、絞り込みは「その値を含む記事」を拾う。
- 軸ごとの絞り込みは **データの中身から動的に生成**（`LABEL_AXES` を変えても
  db_viewer.html自体の編集は不要）。値ごとの件数も表示する。
- **1つの軸で複数の値を選べる**。軸ごとに `いずれか(OR)` / `すべて(AND)` を切り替えられる。
  - `OR` … 選んだ値のどれかを持つ記事（例: 国・地域が「米国」または「中国」）
  - `AND` … 選んだ値を全部持つ記事（例: 国・地域に「米国」と「イラン」の両方がある記事）
    ＝1軸に複数値を持てる設計（§5）があって初めて意味を持つ。
  - **軸と軸の間は常にAND**（国・地域で絞り、さらに業界で絞る）。
- ★フィルタUIを組み直すとき、**`axisFilterBar.innerHTML = ""` で全消ししてはいけない**。
  「フィルタをクリア」ボタンと保存メッセージも同じ親の子要素なので一緒に消え、
  直後の `insertBefore(wrap, clearBtn)` が
  `The node before which the new node is to be inserted is not a child of this node`
  で失敗して**ビューアが丸ごと表示されなくなる**（実ブラウザで発生）。
  `.axis-group` だけを取り除いて作り直す。
- **絞り込み条件・検索語・並び順はブラウザに保存**され（`localStorage`）、次に開いたとき
  その条件で表示される。「フィルタをクリア」で全解除。
  - 保存に使うキーは `xnews_db_viewer_filters_v1`。
  - 保存済みの値がデータから消えている場合（軸や値を変えた後）は、その値だけ黙って捨てる。
    保存内容が壊れている場合は「条件なし」で開く。
  - プライベートウィンドウ等で保存できない場合は、画面右に
    「条件を保存できません（ブラウザ設定）」と出るが、絞り込み自体は動く。
- JSでのDOM操作・フィルタ・保存の一連の挙動は、jsdom（Node.js上で動く実際のDOM実装）で
  `db_viewer.html` をそのまま読み込んで検証している（手書きDOMスタブでは
  `innerHTML=""` の子要素削除などの挙動を見逃したことがあったため、実装の近い環境で確認する
  方針にした）。

## 9. db_viewer の自動起動（`open_db_viewer`）

- メール送信後（成否問わず）、`write_viewer_data()` で `data/news_data.js` を最新化してから、
  `webbrowser.open()` で `db_viewer.html` を **`file://` のURLとして直接開く**。
  サーバプロセスは一切起動しない。
- ★旧版にあった「ポートの空き確認」「別プロセスとの判別」「サーバの多重起動防止」は、
  サーバそのものが無くなったことで**すべて不要**になった。
- `--check-viewer` で `news_log.db` / `news_data.js` / `db_viewer.html` の3点の有無・件数を
  確認できる（ポートは確認しない。確認するものが無いため）。

## 12.5 初期状態（DBなし）での実行

`data/` フォルダごと無い状態から実行しても動く。**検証済み**の挙動：

- `run()` の冒頭で `data/` を作成し、`news_log.db` と `state.json` を自動生成する。
- `config.ini` が無くても落ちない（Xはゲストへ退避、メールは送信時に `[FAIL]` 表示）。
- ゲストトークンの取得に失敗しても**全体を落とさない**。ゲストが必要な垢だけを
  `[FAIL]` にして先へ進み、DB作成・state保存・サマリ表示までは必ず到達する
  （以前はここで例外終了し、初回実行が何も残さず落ちていた）。
- 全垢が捨て垢セッションで動く設定なら、ゲストトークンの取得自体を行わない。
- 収集0件のときはメール送信も `db_viewer` 起動も行わない（`new_ids` が空のため）。
- `db_viewer.html` をデータ未生成の状態で開いた場合は
  「一度実行してください」というメッセージを画面に表示する（白画面にしない）。

## 12.55 db_viewerが表示されないときの確認方法

```powershell
python src\x_collector.py --check-viewer
```

- `news_log.db` / `news_data.js` の件数と生成時刻（データが入っているか、古くないか）
- `db_viewer.html` の有無
- サーバは使わない構成なので、ポートの確認は不要（§9）

画面は出るのに0件のときは、**絞り込み条件がブラウザに残っている**可能性が高い
（条件は `localStorage` に保存される仕様。§8）。db_viewer上部の「フィルタをクリア」を押す。

## 12.6 取得漏れの確認方法

実行ログの各垢の行を見る。

```
[OK] @financialjuice(🔐auth): 新規 54 件 / 保存 54 件（raw 81 / pages 4 / prev=None / 打ち切り=窓を覆った）
     └ 内訳: 窓/差分後54件 → 著者不一致-0 RT-0 引用-0 = emit 54件 / 最新投稿=09/24 13:01（0.3h前）
```

- `打ち切り=窓を覆った` … 窓の端まで到達済み。**取りこぼし無し**。
- `打ち切り=cursorが無い` / `MAX_PAGES到達` … 途中で打ち切り。`[ALERT]` が出る。
- `内訳` … 窓内なのに配信されなかった件数の理由（RT/引用/著者不一致）。
- `取得範囲` … 取れたツイート全体の時間幅と投稿頻度。件数が少ないときは、ここで
  **①取れていない ②フィルタで落ちている ③その時間帯に投稿が無い** を切り分ける。
  - 例: `@DeItaone … 打ち切り=窓を覆った / 内訳: 著者不一致-0 RT-0 引用-0 /
    最新投稿=09/24 05:51（7.8h前）` → 窓は覆えており、フィルタでも落ちていない。
    タイムライン自体の最新が7.8時間前＝**その垢が投稿していない**。
    `@DeItaone` は米国市場のヘッドライン中心で、05:51 JST は米東部16:51（大引け直後）。
    窓が米国の夜間にかかると件数が落ちるのは仕様どおりの挙動。
- `page1: 21件（新規21 / 窓内20） 03/08 13:18〜09/24 13:18 cursor=有`
  … 時間幅の左端が極端に古い場合はピン留めツイート。`cursor=無` ならページ送り不可。

## 13. 既知の制約・リスク・未検証事項（正直ベース）

- **X利用規約違反を前提とした実装**（非公式APIのスクレイピング）。凍結・仕様変更リスクを
  受容する前提（要件P2/P3）。
- `queryId`・`features`・カーソルのキー名はXが随時変更する。**動かなくなったら
  まずDevToolsで現行値を採り直す**（§4.1, §4.2）。
- 捨て垢が凍結された場合は新しい捨て垢を作り直す（`auth-session-setup.md` §4）。
- 指定した時間帯だけを対象にするので、**実行し忘れた時間帯は自動では埋まらない**
  （後から `--from`/`--to` で取り直せるが、送信済みIDより古いものは差分除外で出ない。§4.4）。
- 1ページ約20件なので、**投稿頻度が25件/時を超えるアカウントは8時間ぶんで
  `MAX_PAGES=10`（約200件）を超え得る**。超えた場合は `[ALERT]` が出るので、
  `MAX_PAGES` を上げるか実行間隔を短くする。
- `extract_cursor` のキー名は依然として未検証。ページ送りが1で止まり `cursor=無` が
  続く場合はここを疑う（§4.2）。
- ラベリングの精度・翻訳の質はモデル依存。`LLM_MODEL` の差し替えで調整する。
- **無料枠の上限はGroq側の都合で変わりうる**。上限に当たると待ち時間が伸びるだけで
  止まりはしないが、件数が多い日は実行時間が延びる。
- 推論モデルは1件あたりの消費トークンが大きい（推論ぶんを含むため）。
  6,000トークン/分の枠だと**毎分3〜5件程度**になり、100件超なら20〜35分かかる計算。
  速度が必要なら `openai/gpt-oss-20b` や非推論モデルに替える。
- 1日あたりのリクエスト数にも上限がある（モデルにより1,000回/日など）。
  1回の実行で「記事数＋軸数」ぶん呼ぶので、1日数回の運用なら収まる想定。
- 軸を `LABEL_AXES` から外しても `db_viewer.html` には旧軸が残って見える（§6参照）。
- `EMAIL_GROUP_BY` の値が想定外に多岐（例：国名がバラバラすぎる）だとセクション数が
  増えすぎる可能性がある。§6.5の正規化で軽減するが、粒度はモデル依存。
- **正規化はLLMの判断に依存する**。誤った統合（別物を同じ表記に寄せる）を完全には防げない。
  実機で観測した誤り: `-` → `経済政策`（「なし」に寄せるべき）、
  `IMF` → `国際貨幣基金`（正しくは国際通貨基金）、`中国・米国` `米中` `韓国・米国` が
  分割されずに残る。**軸ごとの許可値リストを持たない限り、この種の誤りは残る**。
  ラベルは毎回上書きされるため、**統合前の値は残らない**。
- db_viewerで見えるデータは **`news_data.js` の生成時点のもの**（サーバを廃止したため
  常時最新にはならない）。最新を見たい場合は `x_collector.py` を再実行してから
  db_viewer.htmlを開き直す（開きっぱなしのタブは自動更新されない）。
- **（クラウド運用時）GitHub Actionsのスケジュール実行は数分〜数十分ずれることがある**。
  `--window 24` で毎回「実行時刻から遡って24時間」を集める設計にしているため、
  多少のズレは前回分と重複するだけで取りこぼしにはならない（重複はtweet_idで自動的に除外）。
  ただし実行そのものがスキップされる（GitHub側の障害等）と、その回だけ穴が空く可能性はある。
- **（クラウド運用時）スケジュール実行は60日間リポジトリに動きが無いと自動停止する**仕様が
  GitHubにあるが、本ワークフローは実行のたびに`data/`をコミットするため、通常運用していれば
  この停止条件には当たらない。
- **（クラウド運用時）`data/`配下を毎回コミットするため、リポジトリのサイズは実行のたびに
  少しずつ増える**。1回あたりのデータ量は小さい（保持期間7日ぶんのみ）が、履歴は積み上がる。
  無料枠内で長期間は問題ない想定だが、気になれば数か月おきに履歴を整理してもよい。

## 14. クラウド運用（GitHub Actions + Cloudflare）

ローカル（Windowsタスクスケジューラ）の代わりに、GitHub Actionsで毎日1回自動実行し、
ビューアをCloudflare Pages + Access（Googleアカウント限定）で公開する構成。
セットアップ手順は `docs/CLOUD_SETUP.md` に分離してある。要点のみここに記す。

- 実行頻度は**1日1回**（既定: 08:13 JST）。`.github/workflows/xnews.yml` の `cron:` で変更可。
- 時間帯指定（`--from`/`--to`）ではなく **`--window 24`**（実行時刻から遡って24時間）を使う。
  1日1回の運用ではこちらのほうがスケジュールの多少のズレに強い（§13）。
- 秘密情報は `config/config.ini` の代わりに **GitHub Secrets** に登録し、ワークフローが
  環境変数として渡す（§10の対応表、`secret()`関数）。
- 状態（`data/news_log.db`・`data/state.json`）とビューア用データ（`data/news_data.js`）は、
  実行のたびにワークフローがリポジトリへコミット・pushして次回実行に引き継ぐ
  （ローカル運用では`data/`はGit管理しないが、クラウド運用ではあえて管理する。
  `.gitignore`参照）。
- CI環境（`GITHUB_ACTIONS=true`）では `open_db_viewer()` はブラウザを起動しようとせず
  自動でスキップする（§9）。ビューアはCloudflare Pagesの公開URLから見る運用のため。
